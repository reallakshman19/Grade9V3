# Governed LOCAL interaction delivery

The Study side owns the canonical target. The Interactive side researches and implements its learner decisions. `interaction_brief.py` derives the brief and academic digest. Missing reuse infrastructure never restricts research. Discovery is advisory and reconstructable.

## Build and use

1. Search `interaction_discovery.py --target-ref ID`, `--representation-ref ID` or `--mechanic-ref NAME`. Stale/invalid sources are reported independently while valid discoveries remain usable.
2. Store the implementation under the subject's `interactions/` directory. A `.local.json` source pins its academic basis and names its stable implementation key. Declarative workbench scenes use the existing adapter. A locally necessary code module can register a mount with the existing portable host; its reference and exact SHA-256 are recorded in `runtime_module`. This is a governed, subject-owned LOCAL module, not a SHARED capability claim or page-local script.
3. A `.reuse-consumer.json` binds an actual canonical question to that implementation and pins the question's own digest. The ordinary `web_resolver.resolve` and `build_explore_page` consume these registrations. The page package retains the academic and consumer binding receipts. Core assessment rendering remains in `render_core.py`; an EXPLORE page does not replace a source question or expose its answer inside an assessment.
4. Render through the existing EXPLORE builder in PAGES or SINGLE_FILE mode. Exercise the generated page in an actual browser, including arbitrary input, negative input, keyboard, touch, portrait/landscape and offline delivery. Function calls on an empty element do not establish delivery.

## Upgrade without losing identity

Activity identity derives from subject + canonical target + implementation key. Academic, model or code changes produce new scene/adapter/package/binding revisions. The original and revised receipts establish lineage through the stable activity ID; preserve both in evidence. Replacing the underlying pedagogical purpose requires an explicit new key and explained relationship, not silent identity reuse.

Update the module digest when its code changes. A changed academic basis or consumer question requires a fresh readback and explicit repin; compilation does not silently adopt it. Exercise both real consumers against the new package. Record old/new package IDs and both consumer bindings, plus rendered/browser evidence. Staleness invalidates a current-delivery claim while research and prototypes continue.

The Mathematics recovery witness implements point dragging and keyboard movement, a selected x with typed y, live residual, accepted-pair dots/table and a line after three distinct accepted pairs. It accepts arbitrary numeric pairs; it does not substitute four predefined cards. The floating-point acceptance tolerance is disclosed. Same-subject use demonstrates REUSED, not SHARED. Cross-subject extraction is unnecessary until actual consumers justify it.

## Review evidence

Record input/code digests, target IDs, source and consumer revisions, exact package IDs, actual HTML, browser observations, failures and remaining findings in the task evidence. Keep generated previews separate from accepted products. Publication and merge remain Owner decisions. No new CI workflow is part of this recovery.
